# TrackingHub 事件治理工作台纵切设计

## 背景

TrackingHub Web 已经有后台壳子、首页状态卡片、主导航页面壳子、事件接收 API 和 SDK 契约。当前 `埋点治理` 页面仍是通用空状态，无法体现产品的核心业务对象：事件字典、Schema、验收和最近接收结果。

本设计推进第一条治理纵切：在不接真实数据库的前提下，把事件字典与验收工作台做成可浏览、可测试、可扩展的静态业务页面。

## 目标

- 将 `/governance` 从空页面升级为事件治理工作台。
- 展示事件字典列表，覆盖事件名、中文名、项目、平台、状态、负责人和最近接收时间。
- 展示选中的重点事件详情，包括业务目标、触发时机、必填属性和验收检查项。
- 展示验收队列，区分可验收、待修复和 Schema 不一致等状态。
- 保持中文产品文案，事件名、平台、环境、属性字段保持协议命名。
- 保持本轮实现只依赖静态 seed data，为后续 API/数据库接入留下清晰边界。

## 非目标

- 不实现事件字典的新增、编辑、删除。
- 不接 Postgres、ClickHouse 或真实事件查询。
- 不做权限、审批、成员邀请或通知流转。
- 不实现复杂筛选器、批量操作和图表分析。

## 页面结构

`/governance` 使用现有 `AppShell` 和 `PageHeader`，页面主体改为三块：

- 顶部概览：事件总数、待验收数量、Schema 异常数量、最近接收事件。
- 事件字典：用表格展示重点事件，帮助产品、运营和工程快速确认事件状态。
- 事件详情与验收：左侧展示一个重点事件的业务语义与属性契约，右侧展示验收检查结果。

## 数据模型

静态数据继续放在 `apps/web/src/lib/trackinghub/sample-data.ts`，新增导出：

- `governanceSummaryCards`
- `eventDictionaryItems`
- `featuredEventDetail`
- `governanceAcceptanceChecks`

这些导出是页面与组件的唯一数据入口。后续接真实 API 时，页面可以将 API 结果映射为同一结构，组件不用感知数据来源。

## 组件边界

新增 `GovernanceWorkbench` 业务组件，负责组合概览、事件字典、事件详情与验收检查。组件内部可以拆小的私有渲染函数，但不引入新的客户端状态。

保留现有 `StatusBadge` 映射业务状态。表格继续使用 shadcn `Table`，卡片使用 shadcn `Card`，按钮使用 shadcn `Button`。

## 错误与空状态

本轮没有异步请求，因此没有运行时请求错误。组件应保证：

- 长事件名可以换行，不挤压状态列。
- 属性字段与检查项即使数量较少也保持布局完整。
- 验收状态通过 Badge 表达，不只依赖颜色。

## 测试

新增或扩展 Vitest 测试：

- 数据契约测试确认治理数据完整、重点事件存在必填属性和验收检查。
- 组件静态渲染测试确认 `/governance` 工作台包含事件字典、重点事件详情和验收检查。

完成后执行：

```bash
pnpm --filter web test
pnpm --filter web lint
pnpm --filter web build
```
